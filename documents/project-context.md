# Observation Manager

Observation Manager is a web logbook for visual astronomy. An observer records where and when a session took place, which objects they saw, which equipment they used, and what they found. An observing program answers a different question: which targets on a planned list already have observations?

## Domain and navigation

| Concept | What it means here | Where to start |
| --- | --- | --- |
| Session | An observing period with a site, start and end times, weather, equipment notes, and comments. Observations refer back to the session by ID. | [Session routes](../src/app/sessions/sessions.routing.ts), [session schema](../api/routers/session/session.schema.ts) |
| Observation | A log entry for a target. It can reference an observer, session, site, scope, eyepiece, filter, and lens. It records timing, seeing, sky quality, magnification, and a finding. | [Client model](../src/app/shared/models/observation.model.ts), [persisted fields](../api/routers/observation/observation.schema.ts) |
| Target (called “Object” in the UI) | A celestial object with a type, constellation, and sky position. The browser route is `/objects`, the client feature is `target`, and the API collection is `/api/targets`. | [Target service](../src/app/target/shared/target.service.ts), [target schema](../api/routers/target/target.schema.ts) |
| Site and equipment | Sites hold geographical coordinates and elevation. Scopes, eyepieces, filters, and lenses are reusable records that can be selected for successive observations. | [Site schema](../api/routers/site/site.schema.ts), [client equipment models](../src/app/shared/models/equipment/) |
| Observing program | A named list of target IDs. Progress is computed by matching those targets to recorded observations. A second sighting of the same target still counts as one observed target. | [Program schema](../api/routers/observing-program/observing-program.schema.ts), [statistics queries](../api/routers/observing-program/observing-program.store.ts) |

## Runtime architecture

- **Browser.** The root npm package builds an Angular 22 application with Angular Material and RxJS. `main.ts` bootstraps `AppModule`. The root router redirects `/` to `/observations` and lazy-loads feature routes and components. The side navigation has its own link definitions. [Bootstrap](../src/main.ts) · [AppModule](../src/app/app.module.ts) · [routes](../src/app/app-routing.module.ts) · [navigation links](../src/app/navigation-links.ts)
- **Client state.** The global NgRx store has three slices: `auth`, `register`, and `navigationMenu`. Entity screens generally load data through feature services extending `StorageService<T>`. Shared components implement list pagination, add/edit flows, and entity selectors. Admin screens use a local ComponentStore. [Root reducers](../src/app/store/index.ts) · [storage service](../src/app/shared/services/storage.service.ts) · [shared components](../src/app/shared/components/) · [admin store](../src/app/admin/common/base-admin-component.store.ts)
- **Server.** The separate npm package in `api/` builds a TypeScript Express 5 service. It opens a Mongoose connection to MongoDB, then registers resource routers under `/api` and starts listening. Express also serves the compiled browser app from `public/` beside the server bundle, with an index fallback for client routes. [Server entry point](../api/index.ts) · [API mount paths](../api/routers/router-provider.ts)
- **Persistence.** A resource typically has a router for HTTP behavior, a store for queries and reference population, and a Mongoose schema and model for persistence. Shared base classes implement CRUD, sorting, paging, and creation/modification metadata. Start with the resource override when investigating a query. List and detail reads can populate different fields on the same reference. [Base router](../api/routers/common/router/base-entity.router.ts) · [base store](../api/routers/common/store/base-mongoose-store.ts) · [observation store](../api/routers/observation/observation.store.ts)

## Trace a session observation

1. The browser opens `/sessions/:sessionId/observations/new-observation`. The add component loads the session and copies its site and start time into a new observation. “Add and continue” carries the equipment and observing conditions forward to the next entry. [Session routes](../src/app/sessions/sessions.routing.ts) · [add component](../src/app/observations/add-observation/add-observation.component.ts)
2. `ObservationService` supplies the `/observations` resource path and client model to `StorageService`. On save, the model serializes entity references as IDs and dates as ISO strings. The service posts that payload to `/api/observations`. [Observation service](../src/app/observations/shared/observation.service.ts) · [serialization](../src/app/shared/models/observation.model.ts)
3. `ObservationRouter` inherits the create handler. The base store attaches the authenticated creator and timestamps, then writes through the observation model. To list that session's entries, the UI calls `GET /api/observations?session=<id>` with paging parameters. The router passes the session filter to the store, which populates references needed by the table. [Observation router](../api/routers/observation/observation.router.ts) · [session observations screen](../src/app/observations/session-observations/session-observations.component.ts)

## Contracts that affect changes

- **Models cross a serialization boundary.** The browser and API define their own models. The client maps MongoDB `_id` to `Entity.id`. The generic update handler reads the serialized body's `id` for its query. When adding a field, trace the form, client model in both directions, API schema, and any store projections or exporters that consume it. For example, the client serializes rating and language for a finding, while the observation schema persists only `result.description` within that object. [Client entity](../src/app/shared/models/entity.model.ts) · [result model](../src/app/shared/models/result.model.ts) · [observation schema](../api/routers/observation/observation.schema.ts)
- **List responses have a specific shape.** Standard lists accept zero-based `page`, `size`, `sortField`, and `sortDirection`. They return `{ items, pageCount, pages, totalCount }`. Despite its name, `pageCount` is the current page index. Target autocomplete is an exception: supplying both `name` and `maxCount` returns a plain array. [Request parameters](../src/app/shared/services/request-params.model.ts) · [base store](../api/routers/common/store/base-mongoose-store.ts) · [target router](../api/routers/target/target.router.ts)
- **Identity travels with the request.** Login uses Passport Local at `POST /api/users/login`. The browser stores the JWT as `jwtToken`, sends its raw value in the `Authorization` header, and restores the user via `GET /api/users/user`. Base entity routes accept optional authentication for reads and require it for writes. The base store scopes authenticated lists and mutations by `userCreated`. Target listing and program statistics have their own query behavior. The client `AdminGuard` currently returns `false`. [Client auth](../src/app/auth/shared/authentication.service.ts) · [user service](../src/app/users/shared/user.service.ts) · [API middleware](../api/routers/authentication/auth.ts) · [admin guard](../src/app/auth/shared/admin.guard.ts)
- **Exports depend on the resource.** Sessions and observations have TXT exporters. Sites, scopes, eyepieces, filters, and lenses have CSV exporters. The session observations screen passes its session filter to the export endpoint. The XML files in `documents/` are OpenAstronomyLog examples. Catalog CSVs live in `api/data/`. Target and constellation stores have upload helpers, but startup does not invoke them to seed an empty database. [Exporter infrastructure](../api/routers/common/export/) · [session export parameters](../src/app/observations/session-observations/session-observation-export-request-params.model.ts) · [catalog data](../api/data/) · [OAL example](OAL20_simple_example.xml)

## Running and checking the project

The root and `api/` have separate manifests, lockfiles, and dependencies. Install each from the repository root with `npm ci` and `npm --prefix api ci`. Their declared Node engines differ: the root specifies `22.22.3` and the API specifies `20.13.1`. [Root scripts](../package.json) · [API scripts](../api/package.json)

1. Start MongoDB and point `CONNECTION_STRING` at a development database. With MongoDB on its default local port, the PowerShell command is `$env:CONNECTION_STRING = 'mongodb://localhost:27017/observation-manager'`. Set it in the terminal that runs the API.
2. From the root, run `npm run build_server`, then `npm --prefix api start`. For continuous API development, run `npm --prefix api run build:watch` and `npm run start_server` in separate terminals. The latter watches the compiled bundle and uses a Windows-style npm script.
3. In another terminal, run `npm run start_app` and open `http://localhost:4200`. The development client calls `http://localhost:3002/api` directly. The API defaults to port `3002`, and `PORT` overrides it. The README and proxy file mention `3001`, but the default Angular serve target has no proxy configured. [Client environment](../src/environments/environment.ts) · [Angular targets](../angular.json) · [server startup](../api/index.ts)
4. Run `npm test` for the Angular Karma/Jasmine suite and `npm run lint` for the frontend lint target. The API manifest defines a build and no test script. For production, `npm run build` produces both `dist/browser/` and `api/dist/index.js`. Build these before building the Docker image, which copies both outputs. The production client uses `../api`. With `NODE_ENV=production`, the API requires `SECRET` for JWTs. `SESSION_SECRET` configures Express sessions separately. [Dockerfile](../Dockerfile) · [production environment](../src/environments/environment.prod.ts) · [JWT configuration](../api/config/auth-config.ts)
